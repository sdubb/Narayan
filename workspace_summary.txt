Plan Mode End-to-End Walkthrough
================================

This file captures how plan mode behaves end to end, including:
- the user input
- the intent extraction / plan-mode JSON
- the compiler draft
- how the executor selects tools
- what happens when the model asks for more tools
- the final compiled output

Key rules from the codebase:
- Plan mode writes a typed workflow DSL instead of free-form steps.
- `data_engine` is the deterministic record-transform tool.
- `data_extractor` is used first for semi-structured text/PDF/HTML extraction.
- `tool_search` finds exact deferred schemas.
- `request_more_tools` expands an entire core category when the current toolset is too narrow.


How the loop works
------------------

1. User gives a business goal in plan mode.
2. Plan-mode LLM turns that into structured JSON:
   - `data_sources`
   - `write_targets`
   - `actions`
   - `preferred_tool_categories`
   - `preferred_tools`
   - `workflow_dsl`
   - `output_hint`
   - `output_questions`
3. The compiler converts the DSL into concrete tools and arguments.
4. The executor sends the selected tool subset to the model.
5. If the model needs an exact schema, it can call `tool_search`.
6. If the model needs a whole category, it can call `request_more_tools`.
7. The executor intercepts those meta-tools, expands the toolset, and re-runs the same step.
8. The result is reviewed, tested, and saved.


Example 1: Clean rows, score them, and rank them
-------------------------------------------------

User input
----------

```text
Find active customers, clean the rows, compute a score, and rank by engagement.
```

What plan mode infers
---------------------

The plan-mode LLM should infer:
- this is a deterministic record workflow
- `data_engine` should handle the transform steps
- a database fetch may be needed first
- the output should be a ranked record set

----------------------

How the compiler turns this into concrete steps
-----------------------------------------------

The compiler looks at the DSL type:
- `fetch_records` -> `sql_query` or `external_db`
- `filter`, `compute`, `aggregate`, `detect_anomaly` -> `data_engine`
- `llm_worker` -> an LLM reasoning step

For the transform steps, the compiler does not leave the tool choice open.
It hard-selects `data_engine` and builds a pipeline argument.

Example compiled step for the filter
------------------------------------

```json
{
  "id": "step_2",
  "tool": "data_engine",
  "operation": "pipeline",
  "args": {
    "records": "$input.records",
    "pipeline": [
      {
        "op": "filter",
        "condition": {
          "field": "email",
          "exists": true
        }
      }
    ]
  },
  "input_mapping": {
    "records": "step_1.records"
  },
  "output_mapping": {
    "records": "step_2.records"
  },
  "output_schema": {
    "type": "object",
    "properties": {
      "records": { "type": "array", "items": { "type": "object" } },
      "meta": { "type": "object" }
    }
  }
}
```

What the executor sends to the model
-----------------------------------

The executor does not send all tools. It sends a selected subset, typically:
- the planned tool for the step
- a small core set
- any preferred tools or categories
- meta-tools like `tool_search` and `request_more_tools`

For this example, the model might see:
- `ask_user`
- `delegate`
- `tool_search`
- `request_more_tools`
- `external_db`
- `data_engine`
- `file_read`
- `glob_search`

If the selected subset is too narrow, the model can ask for more.

What happens if the model asks for more tools
---------------------------------------------

If the model knows the exact tool name or capability, it uses `tool_search`.

Example:

```json
{
  "query": "deterministic record transforms",
  "tool_names": ["data_engine"],
  "limit": 5
}
```

Executor response:

```json
{
  "status": "loaded",
  "query": "deterministic record transforms",
  "matches": [
    {
      "name": "data_engine",
      "category": "data",
      "description": "Deterministic data engine for tenant workflows...",
      "loaded": true
    }
  ],
  "loaded_tools": ["data_engine"],
  "message": "Use tool_names with exact matches to load the schemas you need."
}
```

If the model needs a whole category instead, it calls `request_more_tools`.

Example:

```json
{
  "categories": ["data"],
  "reason": "Need the full data category because the current toolset does not include spreadsheet operations."
}
```

Executor behavior:
- expands the current toolset with the full `data` category
- deduplicates tools already present
- re-runs the same step with the expanded toolset

Executor response:

```json
{
  "status": "expanded",
  "requested_categories": ["data"],
  "tools_added": ["data_engine", "data_extractor", "pdf_read", "pdf_create", "spreadsheet_read", "spreadsheet_write", "image_process", "image_info"],
  "available_categories": [
    "data: data_engine, data_extractor, pdf_read, pdf_create, spreadsheet_read, spreadsheet_write, image_process, image_info"
  ],
  "message": "Your toolset has been expanded. Use the new tools in your next action."
}
```

Output flow for Example 1
-------------------------

Typical step outputs:
- `step_1` returns `records`
- `step_2` returns filtered `records` plus `meta`
- `step_3` returns computed `records`
- `step_4` returns ranked `records`

Final user-facing result:

```text
Found 10 active customers with valid emails. Ranked by score and ready for review in the workspace.
```


Example 2: Read invoices from PDFs, extract fields, and total by vendor
-----------------------------------------------------------------------

User input
----------

```text
Read invoice PDFs, extract invoice number and amount, then total by vendor.
```

What plan mode infers
---------------------

The plan-mode LLM should infer:
- PDF/text extraction comes first
- `data_extractor` should parse semi-structured content
- `data_engine` should handle the vendor aggregation
- the output should be a structured summary, not free-form prose only

Example plan-mode JSON
----------------------

  "actions": ["read invoices", "extract invoice fields", "group by vendor", "sum totals"],

  "preferred_tool_categories": ["data"],
  "preferred_tools": ["data_extractor", "data_engine"],
  "data_engine_use_cases": ["aggregation", "schema-aligned extraction"],
  "data_engine_limits": ["no free-form scripts", "no browser automation", "no remote execution", "no arbitrary custom code"],
  "needed_connector_categories": [],
  "candidate_connectors": [],
  "missing_capabilities": [],
  "workflow_dsl": [
    {
      "id": "step_1",
      "type": "fetch_records",
      "description": "read invoice text from the uploaded PDF",
      "resource_hint": null,
      "tool_hint": "file_read",
      "args_hint": {
        "path": "{input.file_path}"

How the compiler turns this into concrete steps
-----------------------------------------------

The compiler sees:
- `fetch_records` for the PDF source
- `data_extractor` for field extraction
- `data_engine` for aggregation

The important part is that the compiler does not need the model to invent the exact runtime logic.
It only needs the DSL to say what kind of step this is.

Example compiled output
-----------------------

```json
{
  "compiled_steps": [
    {
      "id": "step_1",
      "tool": "file_read",
      "operation": "read",
      "args": { "path": "{input.file_path}" }
    },
    {
      "id": "step_2",
      "tool": "data_extractor",
      "operation": "extract_structured_data",
      "args": {
        "source_field": "content",
        "schema": {
          "invoice_id": { "pattern": "INV-[0-9]+", "type": "string", "required": true },
          "vendor": { "pattern": "[A-Za-z0-9 ]+", "type": "string", "required": true },
          "amount": { "pattern": "\\$[0-9]+(?:\\.[0-9]{2})?", "type": "number", "required": true }
        }
      }
    },
    {
      "id": "step_3",
      "tool": "data_engine",
      "operation": "pipeline",
      "args": {
        "records": "$input.records",
        "pipeline": [
          {
            "op": "aggregate",
            "group_by": ["vendor"],
            "metrics": {
              "total_amount": "sum(amount)",
              "invoice_count": "count(*)"
            }
          }
        ]
      }
    }
  ]
}
```

What to notice
--------------

- The plan-mode LLM does not need to know the low-level Rust function body.
- It needs to choose the right DSL type and tool intent.
- The compiler maps that intent to actual tool calls.
- `tool_search` is for exact schema discovery.
- `request_more_tools` is for category expansion.
- `data_engine` is the deterministic execution tool for record transforms.
- The output of each tool is part of the next step's input mapping and output schema.

If a workflow is semi-structured, the order is usually:
- read source
- extract structured data
- transform with `data_engine`
- summarize or save

If a workflow is already structured, the order is usually:
- fetch records
- transform with `data_engine`
- optionally aggregate
- write result

That is the core plan-mode pattern.
